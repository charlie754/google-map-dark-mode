## 2. Root causes

### 2.1 Transit ("Transmit") is light in both browsers — REPRODUCED, FIXED
Layers → Transit does not draw over the Roadmap palette. Maps swaps the *whole* base map to a
separate style, `TransitFocused`, on every transport (captured 2026-11-09, Chromium 1234 and
Firefox 153/159):

```
https://www.gstatic.com/maps/res/CompactLegend-TransitFocused-5e6bae4931cec7c0849f0477025453b8
/maps/vt/pb=…!2m6!1e2!2stransit!…!1sset!2sTransitFocused!4e0…      (first-paint raster)
/maps/vt/stream/pb=…!1sset!2sTransitFocused!4e1…                   (stream)
```

No rule matched any of them (rules 1/2 name `Roadmap`/`Terrain`, rules 3/4 match
`(Roadmap|Terrain)`), so the light Transit palette went through untouched.
`CompactLegend-TransitFocusedDark-<v>` exists (HTTP 200, ~2.0 MB, on all three pinned versions);
`TransitDark`, `DarkTransitFocused`, `TransitFocusedNight` 404.

**Fix:** rule 5 `CompactLegend-TransitFocused-<v>` → `-TransitFocusedDark-`, and rules 3/4 gain a
third arm `(Roadmap|Terrain|TransitFocused)`. Self-check `RULE_SAMPLES` carries rule 5 and the
Transit arms of 3/4; the offline corpus gains `legend-transit`, `transit-stream`,
`transit-raster` (real captures) and their already-dark loop guards; the liveness canary requires
`TransitFocused`/`TransitFocusedDark` and pins the current version `5e6bae49…`.

Map-area mean RGB of the screenshot after toggling Transit from the Layers control (trusted
pointer input), ~9 s after the toggle:

|---|---|---|
| Chromium 151 | (208, 223, 227) LIGHT | (37, 52, 73) DARK |

### 2.2 Terrain is light in Firefox — NOT REPRODUCED
Driven live with the 1.0.4 build, by toggling Layers → Terrain with trusted pointer input and by
loading `…/data=!5m1!1e4` directly: Playwright Firefox 153 and **stock Firefox 159.0.1**
(WebDriver BiDi), NYC z14/z17, Colorado z4/z7/z10, google.com and google.com.hk, DPR 1 and 1.5,
with a pre-warmed HTTP cache (Terrain loaded before the add-on was installed), and Transit+Terrain
together. Every run: `CompactLegend-TerrainDark` 200, tiles `!2sTerrainDark!`, map DARK
(e.g. (37, 52, 76) and (40, 55, 76)). No service worker, Cache Storage or IndexedDB on Maps that
could serve a stale light palette.

The most likely explanation for the report is Transit (§2.1): with Transit on, Maps uses the
`TransitFocused` palette, which 1.0.4 never darkened. No Terrain-specific change was made beyond
the Transit fix; rules 2/3/4 already cover Terrain and are now live-checked, not just offline.

### 2.3 GOAT Cam banner ("ads section") never updates in Firefox — REPRODUCED, FIXED
`goatBannerGate()` (background.js) returns false in Firefox unless **both**
`GoatBannerKey.firefoxOnline === true` **and** the optional `technicalAndInteraction`
data-collection permission is granted. 1.0.4 shipped `firefoxOnline: false`, and nothing in the
extension could ask for the permission (content scripts have no permissions API; a temporary
install from about:debugging shows no install prompt). So Firefox never fetched and always drew
the bundled DaGoat banner, while Chrome (no gate) drew the signed GOAT Cam banner. With the gate
forced open in a probe build, the full Firefox pipeline (fetch, ECDSA verify, photo decode,
storage, render) worked first time — the gate was the only blocker. CSP is not a factor (Maps'
CSP is report-only and has no `img-src`).

**Fix (consent model unchanged):**
- `extension/lib/banner-key.js`: `firefoxOnline: true` (the key's own Firefox switch; key bytes
  otherwise identical; the byte-copy pin in `banner-copies.test.mjs` updated with a note).
- New `extension/lib/data-consent.js`, used by the popup and options page: a Firefox-only
  **GOAT Cam banner updates** switch that calls `permissions.request({data_collection:
  ["technicalAndInteraction"]})` from the click (or `remove` to opt out). Hidden in Chrome
  (feature-detected by `data_collection` in `getAll()`).
- background.js: `permissions.onAdded` resumes the banner runner, so a grant made while a Maps
  panel is open takes effect immediately rather than at the next 6-hour timer.

Verified on stock Firefox 159 with the real Firefox prompt and real X11 clicks: popup switch →
"Google Map Dark Mode requests additional data collection" → **Allow** → panel shows the online
GOAT Cam banner; **Deny** → switch returns to off, panel keeps the bundled banner. Chrome 1.0.5:
online banner unchanged, switch hidden.

## Follow-up: "Terrain on is still white" on Windows Firefox (same day)

Report: Windows Firefox, Maps in zh-TW (San Jose), signed in, Terrain on, map surface light while
the panel says Map surface On. Not reproducible here: zh-TW / Accept-Language zh-TW,en at
37.37,-121.95 z13, Terrain toggled from the Layers UI, with and without Transit, DPR 1.25/1.5,
clean and pre-warmed profiles, stock Firefox 159 with the real .xpi -- all dark. In those
sessions Maps fetched `CompactLegend-Terrain-5e6bae…` and the vector tiles with
`!1sset!2sTerrain!`, and both were redirected to the Dark variants.

Root cause (evidence, not a firsthand repro): the live Maps config in the page HTML (base64
protobuf after `["/maps/vt"],803,["/maps/vt/stream"]`) lists, next to the classic pair,
`https://www.gstatic.com/maps/res/CompactLegend-TerrainVectorClient-5e6bae…` and
`…TerrainVectorClientDark-5e6bae…` (both HTTP 200, 2,083,814 / 1,968,178 bytes). Rule 2 was
`CompactLegend-)Terrain(-.*)$`, which requires `-` straight after `Terrain`, so the vector
terrain palette went through untouched. Proven in real browsers: with the efb054b build a
page fetch of `CompactLegend-TerrainVectorClient-…` was NOT redirected (Firefox 159 and
Chromium, 2,083,814 bytes, light) while `Terrain` was.

Fix: rule 2 `CompactLegend-)(Terrain|TerrainVectorClient)(-.*)$` -> `\1\2Dark\3`; rules 3/4
alternations gain `TerrainVectorClient`. After the fix the same fetch lands on
`…TerrainVectorClientDark-…` (1,968,178 bytes) in both browsers. Corpus, classifier tokens,
self-check sample, liveness canary and mutation tests extended; 2 KB detector 43/43.

Unverified: that the user's session actually requested TerrainVectorClient (no signed-in or
GPU Windows session here). Other unmatched palettes in the same config with Dark twins, not
touched: RouteOverview (directions), Travel, AirQualityHeatmap, Navigation*.

## Follow-up: "the terrain mountains are still white" after a512522 (same day)

Report: Windows Firefox, en UI, a512522, Terrain on: water and the road grid dark, but the
mountains (hillshade, beige land, mint vegetation) light; "other plugins can make it dark".

Reproduced on this box once Maps was pushed onto its WebGL renderer (mapcore): an init script
spoofing `UNMASKED_RENDERER_WEBGL` to a real NVIDIA/D3D11 string. Without it, SwiftShader
(Chrome) and llvmpipe (Firefox) always get canvas+labeler, which colours the relief from the
`!2sTerrain!` raster/stream tiles we already rewrite -- that is why z13 tests here were dark.

Root cause: in mapcore, Terrain = vector map coloured by `CompactLegend-TerrainVectorClient-<v>`
(rule 2 since a512522: dark water/roads) + a server-rendered relief layer fetched as
`https://www.google.com/maps/vt/proto?bpb=Cg0KCAgLEMwCGJwGygEAEgsIBRIHc2hhZGluZxIMCAYSCGNvbnRvdXJz…`
(40 of 84 proto requests at San Jose z11). Decoded: layers `shading` + `contours`, style
`62 12 08 44 12 0e 0a 03 "set" 12 07 "Terrain"`. Colours are baked server-side from that name;
no rule could touch it (proto was documented as un-rewritable).

Server checks (curl, same URL): original 200 / 49,272 B (light); properly re-encoded with
`TerrainDark` 200 / 38,277 B (dark); prepended or appended second `set` entry 400. Dropping
style option 63 (`62 02 08 3f`) together with the TerrainDark swap returns a byte-identical
tile to the proper re-encode -- which makes a same-length rewrite possible.

Fix: rules 6-8 (tools/proto-terrain-rules.mjs): the 26-byte region
`opt63 opt3 set=Terrain a0 01` -> `opt3 set=TerrainDark a0 01`, one literal per base64
alignment; all three alignments occur in real traffic (z9/z17, z11/z13/z15, z5). Synthetic tiles
at every alignment rewritten and fetched: all 200. First attempt with an alignment-enforcing
prefix tripped Chrome's 2 KB budget for rules 7/8; the extension's self-check caught it
(`rules-broken`, ruleset auto-disabled) -- prefix is now `[^&]*`, 2 KB detector 49/49.

Other dark-mode extensions: Dark Reader's google.*/maps fix INVERTs the map canvas
(`[role="application"] > canvas`, `.widget-scene-canvas`, …) unless imagery/globe mode -- a CSS
invert of Google's light map. Not used here: inverting a canvas that already has dark vector
parts would turn those light, and invert also hue-shifts pins/photos.

Verification (mountain-region average RGB, Santa Cruz Mtns / Diablo Range, z10, Terrain toggled
from Layers): user screenshot (180,196,191)/(175,197,181); Chrome mapcore a512522
(150,180,163)/(176,198,183) -> fix (25,53,62)/(28,52,65); Firefox 159 mapcore a512522
(149,178,162)/(166,189,179) -> fix (25,52,62)/(29,52,65); Chrome mapcore zh-TW fix
(27,55,63)/(28,52,65); canvas mode (no spoof) Chrome (24,52,61)/(27,51,64), Firefox
(24,52,61)/(35,59,74). UI intact (Layers, controls, attribution), 0 proto 4xx.

## Follow-up: "Chrome: Transit, then Layers → More, still bright" after 1480915 (same day)

Report: Chrome (Windows, real GPU, so the WebGL renderer), Transit on, Layers → More opens
"Map details" and the map is light although the panel says Dark Mode On. Terrain alone stays
dark. Firefox fine.

Reproduction (Chrome, mapcore forced by the spoofed GPU string, Mountain View 37.39,-122.06 z14,
en): a fresh profile stayed dark through Transit, More, Terrain on/off. One profile on this box
(`/tmp/warmprof`, kept) was light from the first paint, with or without More, with the extension
on: average map RGB (226,231,231).

Root cause, from the request log of that profile (URL evidence): no `CompactLegend-<Style>-`
request at all apart from the self-check's own `CompactLegend-RoadmapSatellite/RoadmapDark-e3dec…`
canaries, so rules 1/2/5 had nothing to redirect; all 43 vector tiles were
`https://www.google.com/maps/vt/proto?bpb=…` (200, not rewritten) whose decoded set entry is

    default variant:       62 12 08 44 12 0e 0a 03 "set" 12 07 "Roadmap"            a0 01 ...
    server-styled variant: 62 16 08 44 12 0e 0a 03 "set" 12 07 "Roadmap" 28 01 30 01 a0 01 ...

(and the same for the `transit` layer with `TransitFocused`, and for the Terrain relief with
`Terrain` -- the latter also escaped rules 6-8, whose region ends `"Terrain" a0 01`). Options 5
and 6 make Google bake the style's colours into the tile; the client then needs, and fetches, no
palette. curl, same tile: original 9,726 B; `RoadmapDark` without the two options 9,071 B (the
default-variant dark tile); Transit tile 14,007 B -> 12,867 B; baked Terrain relief 17,228 B ->
14,505 B (identical with or without the options once the style is TerrainDark).

Why Chrome only / why "More": the variant is chosen by Google per browser profile and follows the
profile's Google cookies (deleting Cookies returned the default variant and a newer client build;
deleting the HTTP cache or the Maps service worker `/maps/preview/sw` did not). The user's
Firefox profile was evidently in the default variant. On this box the light map did not depend on
More -- it was light from the first paint in that profile; More (no new map requests) just leaves
the map visible beside the panel. Not proven that the user's profile behaves identically.

Ruled out: a service-worker or HTTP-cache path bypassing DNR (the proto/legend responses were not
`fromServiceWorker`; a profile warmed without the extension still got 307s on cached legend URLs).

Fix: rules 9-17 (tools/proto-terrain-rules.mjs, `SWAPS`): `set=<Style> 28 01 30 01` ->
`set=<Style>Dark` for Roadmap, TransitFocused and Terrain -- same length, so no length prefix or
other base64 character changes; one literal per base64 alignment. Regex sizes 80-90 chars, 2 KB
detector clean. Self-check samples (RULE_SAMPLES 9-17; 9, 10, 12, 16 verbatim from the capture,
the rest re-encoded tile coordinates), corpus MUST_MATCH/MUST_NOT_MATCH (loop guards), and
proto-terrain.test.mjs (derivation, alignment, strict-protobuf decode, Dark token, tile unchanged,
partial-option safe failure, per-rule mutation, background samples == corpus).
